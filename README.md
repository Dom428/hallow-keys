# Hallow Keys

A personal password manager for Windows - part of the Hallow family with [Hallow Hub](https://github.com/Dom428/hallow-hub), [Hallow Mixer](https://github.com/Dom428/hallow-mixer), [Hallow Remote](https://github.com/Dom428/hallow-remote), [Hallow Setup](https://github.com/Dom428/hallow-setup) and the others. Everything stays on your PCs, in one encrypted file - no account and no Hallow server; if you want it on several PCs, it syncs through a folder you already have (OneDrive, Google Drive, Dropbox, a NAS, Syncthing).

> **Not audited.** Hallow Keys hasn't been reviewed by security experts. Keep using a tried-and-tested password manager for anything that matters, and keep backups.

- **Developer tools** (2.6) - an **SSH agent** that serves the SSH keys in your vault to Windows' ssh, git and anything else using Windows' OpenSSH (each use approved in a small prompt or with Windows Hello; Ed25519, RSA and ECDSA keys; git commit signing with SSH keys), and a **command line** (`hk --get`, `hk --env`, `hk --run`) that puts secrets into scripts and `.env` files - every use approved, only while unlocked; both off until you turn them on
- **Passkeys** (2.3) - sign in to websites with passkeys kept in your vault: the extension answers the site's passkey request with Hallow Keys' own prompt (save, pick, or hand it to your phone / security key / the browser), the key signs in the app and never reaches the page, and passkeys sync with the rest of the vault; passkey autofill in the suggestions under the username box
- **Logins, secure notes, cards, identities, documents** with folders, **tags**, favourites, search and small encrypted file attachments (up to 10 MB each), in a sortable table with category tabs (All items, Logins, Passkeys, Secure notes, Cards, Contact info, Documents, Other), **Last used**, site icons or coloured letter tiles, and tick boxes to move, tag or delete several items at once
- **Emergency access** (2.5) - an **emergency package** for someone you trust: an encrypted copy of the vaults you pick that only their Hallow Keys can open (optionally only together with your recovery code), and a full printable **Emergency Kit** with plain-language restore steps
- **Sharing without a server** (2.4) - send one item as an encrypted file with its own passphrase and an expiry, or keep a **shared vault** in a folder your family or team already shares: each member runs their own Hallow Keys, joins with their **member card** (a public key with a fingerprint to compare), and everything is encrypted to each member's key; removing someone changes the key
- **Several vaults** - Personal, Gaming, Work, Shared... each item in one; switch at the top of the sidebar, move items between them, export one on its own; **Travel Mode** hides every vault not marked "safe for travel" from this PC until you turn it off with your master password
- **Every kind of item** - SSH keys (key type and fingerprint worked out, new RSA keys made by Windows), API credentials, software licences, bank accounts, passports, driving licences, Wi-Fi networks, servers / databases, memberships and crypto wallets; **your own fields** on any item (text, hidden, web address, date, 2FA, email, phone) and **your own templates**; several websites per login
- **Expiry dates** - cards, passports, licences, memberships and your own dates in an Expiring view, in Password Health and as a reminder before they run out
- **Quick search** - an optional global shortcut (off by default; turn it on in Settings, Ctrl+Shift+Space or your own) opens Hallow Keys with the search box ready; every word you type has to match, `#tag` finds a tag, Enter opens the best match
- **Password history** - each login keeps its last 10 passwords (with the date each was replaced), to show or copy
- **Trash** - deleted items can be restored for 30 days; a **duplicate finder** for the same account saved twice
- **Generator** - random characters or passphrases, made with Windows' cryptographic random numbers
- **Password Health** - one security score (with its formula) and "fix these first": weak, reused, old and leaked passwords (an opt-in check against Have I Been Pwned), sites breached since you set the password, sites that offer 2FA you haven't set up, http addresses and expiring items - with one-click fixes
- **2FA codes** built in (TOTP from `otpauth://` links or setup keys)
- **Import** from NordPass (CSV export), other CSV exports and Bitwarden (unencrypted JSON); after importing it offers to delete the plain-text file
- **Encrypted backup** of the whole vault, an **encrypted export** with its own password, a **plain CSV export** (behind a warning and your master password), a printable **recovery sheet**, master password change
- **Auto-lock** after idle minutes, when Windows locks and when the PC sleeps; copied passwords leave the clipboard after 20 seconds and never go into Windows' clipboard history
- **Browser autofill** (Chrome, Edge, Brave, Opera, Opera GX, Vivaldi, Arc, Chromium, Yandex and Firefox) - logins, 2FA codes, cards and addresses; suggestions under the box you click into; fills only when you pick something, logins only on the site they were saved for, cards and addresses only on https pages, never into hidden boxes; two-step sign-ins; offers to save new logins and sign-ups
- **Desktop app autofill** (opt-in) - a shortcut you pick types the username, Tab and password into Steam, Battle.net, Riot Client, Epic, EA app, Ubisoft Connect or any program you add to a login; never into games, full-screen windows or programs running as administrator
- **On your phone** through [Hallow Remote](https://github.com/Dom428/hallow-remote): an optional copy opened on the phone with your master password (HTTPS only) - and with **Let the phone edit** (2.7) a full editor: add, edit, move to the trash, generate passwords, 2FA keys, folders and vaults, every change sealed on the phone and checked by Hallow Keys; one-time **share links** for a single item
- **Sync between your PCs** through any folder you choose - merged item by item, real conflicts kept as copies, works offline; a **Secret Key** (like 1Password's) and **Argon2id** so a copy of the vault in the cloud can't be attacked by guessing your master password; a printable **Emergency Kit**; **Restore an older version** from encrypted snapshots
- Optional **Windows Hello** unlock (convenience, not extra security - see below)

## Developer tools (2.6)

Both are in **Settings > Developer tools**, off until you turn them on, and only work while Hallow Keys is unlocked.

**SSH agent.** Turn on *SSH agent*, then tick the SSH key items to offer (only OpenSSH-format keys without a passphrase - they're already inside your encrypted vault; to remove a passphrase: `ssh-keygen -p -f <file>`). Windows' ssh, ssh-add, ssh-keygen and anything else using Windows' OpenSSH then see them on the standard pipe `\\.\pipe\openssh-ssh-agent`. Check with `ssh-add -L`. Each signature asks first (the prompt names the program and the key; "don't ask again for N minutes" is per program and key and forgotten when Hallow Keys locks), or uses Windows Hello if you switch that on. Adding or removing keys from outside (`ssh-add <file>`) is refused - the keys live in the vault.

If Windows' *OpenSSH Authentication Agent* service is running it owns the standard pipe; Hallow Keys doesn't stop or change it (that's a Windows setting). Turn on *Use Hallow Keys' own pipe* and point ssh at it:

```
$env:SSH_AUTH_SOCK = '\\.\pipe\hallow-keys-ssh-agent'     # PowerShell, this window

# or for every program, in %USERPROFILE%\.ssh\config (forward slashes: ssh treats \\ as an escape)
Host *
  IdentityAgent //./pipe/hallow-keys-ssh-agent
```

**Git.** Git for Windows comes with its own ssh, which can't reach Windows' agent pipe - point git at Windows' OpenSSH:

```
git config --global core.sshCommand C:/Windows/System32/OpenSSH/ssh.exe
# commit signing with an SSH key from the vault
git config --global gpg.format ssh
git config --global gpg.ssh.program C:/Windows/System32/OpenSSH/ssh-keygen.exe
git config --global user.signingkey "key::ssh-ed25519 AAAA... (the key's public key line)"
git config --global commit.gpgsign true
```

Each signed commit asks once (or not, within a remembered approval). To check signatures: `gpg.ssh.allowedSignersFile` with lines like `you@example.com ssh-ed25519 AAAA...`, then `git log --show-signature`.

**Command line.** `hk.exe` is in Hallow Keys' folder (`%LOCALAPPDATA%\Programs\Hallow Keys`); `HallowKeys.exe` takes the same arguments, but use `hk.exe` in scripts - shells wait for it and get its exit code.

```
hk --get "GitHub"                          # the password
hk --get "GitHub" --field username         # username, password, totp (the current code), notes, url, or any field by name
hk --get "Example API/credential"          # item/field
hk --env .env.template --out .env          # fills {{hk:Item/field}} placeholders; never overwrites a file (no --out: stdout)
$env:DB_PASS = 'hk:Database/password'      # variables set to hk:item/field ...
hk --run -- npm start                      # ... are filled in for the command it starts (and --run --env <template> adds NAME=value lines)
```

Every request shows a prompt naming the program that asked (e.g. "hk.exe (from powershell.exe)") and the items and fields; a wallet's recovery phrase and passkeys are never given out. Nothing is logged except "who asked for which item" in the Activity list. Exit codes: **0** ok, **1** usage, **2** Hallow Keys isn't running, **3** locked, **4** item or field not found (or several items have that title), **5** not allowed (or no answer in 60 seconds), **6** the command line is turned off, **7** other error; `--run` returns the command's own exit code.

## How it's built

- **Master key (2.0):** Argon2id (RFC 9106, version 0x13) with 256 MiB, 4 passes and 4 lanes and a random 16-byte salt - written out in C# (Windows has none) and checked against the RFC 9106 test vectors (Argon2d, Argon2i, Argon2id) and the reference implementation's test vectors; BLAKE2b is checked against RFC 7693. The result is combined with the **Secret Key**: KEK = HKDF-SHA256(Argon2id(password) || Secret Key, salt = the vault id, info = `HallowKeys 2SKD v1`) (HKDF checked against RFC 5869). The key wrap's associated data binds the vault id, the KDF and its parameters and the Secret Key's id. Vaults from 1.x keep PBKDF2-HMAC-SHA256 (600,000 rounds) until you click Upgrade protection; Argon2 parameters in a header are bounded (at most 1 GiB) so a changed file can't make it allocate without limit.
- **Secret Key:** 128 random bits from the system CSPRNG, written `HK-XXXXXX-XXXXXX-XXXXXX-XXXXXX-XXXXXX`: 26 base32 characters (no 0/O/1/I) and 4 check characters (20 bits of SHA-256), so a typo or swapped pair is caught before anything is tried. Kept on each PC in `secret-key-<vault id>.bin`, protected with DPAPI for your Windows account, and inside the encrypted vault (so a PC that's unlocked learns a new one made on another PC). The header holds an 8-byte id of it, so the wrong key is reported at once. It is never written in plain text anywhere else - not in settings, status, logs or crash reports.
- **Recovery code:** 160 random bits that wrap the same data key on their own (PBKDF2-SHA256, 600,000 rounds - the code itself is unguessable). It opens the vault **without the Secret Key**, on any PC; you then pick a new master password (the Secret Key is kept if the vault or this PC has it, otherwise a new one is made and a new Emergency Kit shown).
- **Envelope:** a random 256-bit data key encrypts the vault; the master key (and, separately, the recovery code) wraps the data key. Changing the master password only re-wraps the key.
- **Encryption:** AES-256-GCM from Windows' CNG (`bcrypt.dll`) - the only hand-written cryptography is Argon2id / BLAKE2b, checked against the published test vectors - with a fresh random 96-bit nonce every save, and the whole header authenticated as associated data.
- **File:** `%APPDATA%\HallowKeys\vault.hkvault`, a versioned format with magic bytes (2.1 writes **format 4** - the same layout as 2.0's format 3 -: the KDF and its parameters, flags, a random vault id, the Secret Key's id and the key blocks' change times in the authenticated header). Saves are atomic (temp file, then replace) and the previous good file is kept as `vault.hkvault.bak`; encrypted snapshots go to `versions\` (at most one every 10 minutes, the newest 30 kept). A wrong password or a changed file is reported and never "repaired".
- **Sync (2.0):** each PC keeps its own vault; the copy in the sync folder is `vault.hkvault`. Every item carries a version vector (changes per PC), a SHA-256 of its content, the time and the PC; deleting for good leaves a tombstone. Merging is per item: the side that has seen the other's changes wins; concurrent changes to the same item keep the later one and add the other as a conflict copy with an id both PCs work out the same way (so it appears once); an edit beats a concurrent delete. Password changes, new recovery codes and Secret Keys travel as the newest key block (the data key never changes). The folder copy is written whole to a temp file and swapped in, retried while a cloud client holds it, and never written while the copy there can't be read (a cloud client still writing it - after 10 unchanged minutes it's set aside as `.hkvault-damaged`, never deleted). Conflict files are merged and then moved to `sync-merged\` on this PC. A folder holding a different vault is never written to (Settings offers to join it). Sync runs in the background on a copy of the vault; changes that came in are merged into the open vault, keeping anything you typed meanwhile. status.json and the family pipe get only the sync state, the service's name and the time - never a path, key or item.
- **Vaults and Travel Mode (2.1):** a vault is a record inside the encrypted vault (id, name, icon, colour, safe for travel, deleted, and a change time for each of those); an item names its vault (`VaultId`, left out for Personal so 2.0 items keep their content hash and nothing re-syncs on upgrade). Sync merges each vault setting on its own by its time; a deleted vault stays as a marker and an item whose vault is gone shows in Personal - nothing is ever dropped. Travel Mode is a setting of this PC: one filter decides what the window, the extension's answers, desktop autofill, the phone copy, exports, the status item count and Password Health may see. It hides, it doesn't remove: the items stay in the encrypted vault file and keep syncing. Moving the hidden items out to a separate "travel-hold" file was considered and left out - with sync it could make other PCs delete them, and that risk isn't worth it.
- **Last used (2.1):** a list of (item, time) inside the encrypted vault, outside the items' revisions (using an item never makes it "changed" or causes a conflict); merged by the latest time; times of items that are gone are let go. Never in status.json, the pipe, settings or logs.
- **Site icons (2.1, opt-in):** only for a login's first https address with a public name: names that are IP addresses, single labels, `localhost`, `.local`, `.lan`, `.internal`, `.home.arpa` and similar are refused, and so is any name that resolves to a private, loopback, link-local or carrier-grade NAT address. `https://<host>/` is read (at most 256 KB) for `<link rel="icon">` (https, same registrable domain, no SVG or data:), then `/favicon.ico`; at most 3 redirects, https and same registrable domain only; 6 s timeouts; no cookies, credentials, Referer or disk cache; a generic browser User-Agent. Images must be PNG, ICO, GIF or JPEG by their first bytes, at most 100 KB and 512x512 pixels, and are redrawn as 32x32 PNGs. The cache `icons.hkcache` is AES-256-GCM with a key derived (HMAC-SHA256) from the vault's data key, and the sites in it are HMACs - neither the sites nor the pictures can be read without unlocking. Not synced (each PC fetches its own); turning the setting off deletes it.
- **Windows Hello** (off by default): the data key is protected with DPAPI for your Windows account and handed back only after Windows Hello confirms it's you. Anything that can run as you on this PC could get at it, so it's for convenience, not stronger security.
- **Memory:** key and plaintext byte arrays are wiped after use, and the vault is dropped when it locks. .NET strings (the items while the vault is open, text in the window) can't be wiped - they stay in memory until the garbage collector reuses it.
- **New in 1.3, all inside the encrypted vault:** password history (and the dates), tags and the trash are part of the encrypted items - the file format and its encryption are unchanged. Items in the trash don't fill, don't count in Password Health and don't go to the phone copy; after 30 days they're removed when you unlock.
- **Exports:** the encrypted export is the same file format with its own random data key, its own salt and Argon2id (2.0; PBKDF2-SHA256 before) from the password you pick, no Secret Key and no recovery code - your master password doesn't open it. An encrypted backup is the vault itself: master password and Secret Key, or the recovery code. The plain CSV export asks for your master password first; text that a spreadsheet would treat as a formula gets a leading `'` (Hallow Keys' import removes it), passwords are written exactly as they are, and the trash isn't exported.
- **Quick search shortcut:** registered with Windows' RegisterHotKey on a hidden message window. If another app already has the combination, Windows refuses and Hallow Keys leaves it off (it never takes a shortcut away from another app) and tries again every few minutes.
- **New in 1.5:** the Apps field lives inside the encrypted vault like everything else; the file format and its encryption are unchanged. Cards: the app answers only on https pages, the card list shows titles and the last 4 digits, and the security code is sent only when the extension asks for it (your second click, or its setting). Card numbers are never logged.
- **New in 1.7 (Password Health):** the breached-sites list (`haveibeenpwned.com/api/v3/breaches`) and the 2FA list (`api.2fa.directory/v3/totp.json`) are fetched with a plain GET - no query, no cookies, no key, nothing about you - only when you click or weekly if you opt in, checked before they replace the copies in `%APPDATA%\HallowKeys` (a broken or empty download never replaces a good copy), and matched against your logins by registrable domain on this PC. Made-up ("fabricated") breaches and spam lists are ignored. A login counts as breached when the breach date is on or after the day its password was set (imported logins count from the import, as the real date isn't known). The score is the average of per-login scores (100 minus 40 leaked, 30 breached, 25 reused, 25 weak, 10 each for 2FA available, http and old), minus 5 per expired item (at most 20).
- **New in 1.6:** the new types, your own fields, templates and reminder bookkeeping are all inside the encrypted items. The vault file is now **format 2** (same layout and encryption): Hallow Keys 1.5 and older refuse it with "made by a newer Hallow Keys" instead of opening it and dropping 1.6 fields on their next save; 1.6 opens format-1 vaults and saves them as format 2 (the previous file stays as `.bak`), and keeps any data it doesn't understand from a later version. SSH fingerprints are SHA256 of the public key blob, as `ssh-keygen -l` shows them (checked against Windows' own `ssh-keygen`); generated keys are RSA from `RSACng`, written unencrypted in OpenSSH's format because they live inside the encrypted vault. The phone copy shows the new types in Hallow Remote 1.10's existing layout (visible fields in the notes, hidden ones behind Show).
- **Desktop app autofill:** off by default and no shortcut until you pick one (nothing is registered with Windows before that). The program in front is matched by its exe name against the Apps field of your logins. It refuses when Keys is locked (it opens so you can unlock), when the program isn't on a login, when the window is full screen, when a game is running (Hallow Overlay's live stats or Hallow Hub's "playing" list - launchers still work), and when the program runs as administrator but Keys doesn't. It waits for you to let go of the shortcut keys, checks the same window is still in front, then types with `SendInput` and `KEYEVENTF_UNICODE` (each character as itself, never through the clipboard), Tab between username and password, never Enter - and stops if another window comes to the front. Several matches show a small chooser.
- **Nothing secret leaves the vault:** not in logs, crash reports (anything from the open vault is blanked out of them), status files, the family pipe (it answers only ping, status - locked or unlocked and the item count -, open, menu and invoke), window titles or `--snap` pictures (made-up items only).
- **Generator:** `RNGCryptoServiceProvider` with rejection sampling (no modulo bias).
- **Leak check:** Have I Been Pwned's range API with the `Add-Padding` header; only the first 5 hex characters of each password's SHA-1 leave the PC, and the match happens locally. Only when you click, or weekly if you turn that on.
- **Phone copy:** `phone.bin` next to the vault, AES-256-GCM under its own PBKDF2-SHA256 key (600,000 rounds, own salt) from your master password; Hallow Remote serves only that file and only over HTTPS; the phone decrypts it with WebCrypto (view and copy only, locks after 2 minutes or when you leave the page). The phone key is kept inside the encrypted vault.
- **Emergency packages (2.5):** `.hkemergency`: a header (sender's name and fingerprint, the contact's name and member id, date, vault names, item count, whether the recovery code is needed, its salt) and the chosen vaults' live items under a random 256-bit key with AES-256-GCM (the header as associated data). The key is sealed to the contact's member card (ECDH P-256 + HKDF + AES-GCM, as in 2.4); with the recovery code, PBKDF2-SHA256 (600,000 rounds, own salt) of the code is mixed into the HKDF input, so neither the contact's key nor the code opens it alone. Changing any byte (including "needs the code") makes it fail. The code is checked by opening your vault with it before the package is made. Imported items get new ids, an "emergency" tag and their own vault.
- **Sharing (2.4):** each vault gets a member identity: an ECDH P-256 key pair made with CNG; the private key lives only inside the encrypted vault (and syncs with it). A member card is `HKM1-` + base64url(name, public key) + 4 check characters; the fingerprint is 20 base32 characters of SHA-256(public key). **Sealing to a member**: a fresh ephemeral P-256 key, ECDH with the member's key (CNG), SHA-256 of the shared secret, HKDF-SHA256 (salt = both public keys, info = the purpose and ids), AES-256-GCM. **A shared vault** is one file, `shared.hkshared`: a header (id, name, key number, members with their public keys and the content key sealed to each, the removed members' names, the key-change proofs) and the items (2.0's item format with revisions and tombstones) under a random 256-bit content key with AES-256-GCM, the whole header as associated data - a changed name, member list or byte is refused. Removing a member makes a new content key ("key 2", "key 3"...) sealed to the members left, with a proof HMAC-SHA256(old key, key number | hash of the new key). Each member's vault remembers the shared vault's current key (inside the encrypted vault), so it refuses a file with an older key number (an old copy put back), a file at the same key number with a different key (a look-alike file someone made with your public member card), and a new key without a proof made with the key it knew (a removed member or an outsider can't start a new key). The first time you join, nothing is known yet - check the members' fingerprints then. Members' copies written at the same time (cloud conflict files) are merged with 2.0's rules and then moved out of the folder to `shared-merged\` on that PC. **Item share files** (.hkshare): the item (without its password history, desktop apps or vault) as JSON, AES-256-GCM under Argon2id(passphrase, 64 MiB, 3 passes, 4 lanes, random salt); the expiry, the date and the sender's name are in the authenticated header (moving the date breaks the file). The passphrase is six generated words; Hallow Keys refuses expired files, which only Hallow Keys can promise.
- **Passkeys (2.3):** WebAuthn Level 3 as a synced, platform-style authenticator. The extension puts a small script into https pages (top page and same-origin frames only, before the page's own scripts) that wraps `navigator.credentials.create` / `get` for `publicKey` requests only - passwords, federated logins and cross-origin frames go straight to the browser - and talks to an isolated content script that shows the prompt in a closed shadow root and acts only on real clicks. The app checks again: https only; the rpId must be the page's host or a parent domain that is still a registrable domain (never a public suffix like `com`, `co.uk` or `github.io`, never an IP address), the origin in `clientDataJSON` comes from the address of the frame that asked, never from the page. Keys are **ES256** (ECDSA P-256 / SHA-256) made and used with Windows' CNG; the private key (the 32-byte scalar) lives only in the encrypted vault and signs in the app - the browser gets `clientDataJSON`, the authenticator data, the DER signature and the public key. Registration returns attestation **"none"**, Hallow Keys' AAGUID `b7e3f1a4-5c2d-4e8f-9a61-0d3c8e2f47b5`, flags UP, UV, BE and BS (backed up, like other synced passkeys), sign count 0, transports `hybrid` + `internal`, attachment `platform`; credentials are discoverable (credProps rk). User verification is "Keys unlocked + a click in its prompt", plus Windows Hello first when Windows Hello unlock is on. excludeCredentials is honoured (InvalidStateError); the same account saved again replaces the old passkey (it goes to the trash). Only ES256: a site that allows only EdDSA or RSA is handed to the browser. The private key is a hidden field that is never displayed, copied, searched, put in the phone copy or written to CSV, and it is blanked out of crash reports like every vault value.
- **Browser extension:** a Manifest V3 extension with a fixed ID. The browser starts `HallowKeys.exe` as a native messaging host (registered per user under HKCU when you click Connect browsers); it answers only that extension ID, never reads the vault, and passes requests to the running, unlocked app over a pipe with a per-session secret. Logins are offered only on the exact host or the same registrable domain (look-alike Unicode names don't match, and https logins are never offered on http pages), filled only after a click, only into visible boxes in the top page or same-origin frames. For 2FA the extension gets only the current 6- or 8-digit code of a login that matches the page - never the 2FA key. The suggestions under a box live in a closed shadow root (the page can't read them) and hold only titles, usernames and a card's last 4 digits; nothing secret goes into the page until you pick an item, and only real clicks and key presses count. The 2FA code after a password fill is filled automatically only in the same tab, on the same site (checked again by the app), within 2 minutes, once. Payment boxes inside a cross-origin frame (Stripe-style) are never filled.

Built with the C# compiler that ships with Windows (.NET Framework 4.8): run `build.ps1`. No admin needed.

Click **Connect browsers** on the **Browser** page in Hallow Keys first (once per PC; again after installing a new browser). Then load the extension from the `extension` folder next to `HallowKeys.exe` (the Browser page has a **Copy folder path** button). It always gets the same ID (`nakjoajpklglfbaallnjofphmnhbedfo`), which is the only one Hallow Keys answers.

## Publishing to the Chrome Web Store / Firefox Add-ons

Not done - this is what it would take, for you to decide. The package's `store` folder has `hallow-keys-chrome-web-store.zip` (the extension without its fixed `key`, as the stores want), `hallow-keys-firefox-addons.zip`, `LISTING.md` (name, descriptions, permission and data-use answers, screenshot list) and `PRIVACY.md` (a privacy policy draft).

- **Chrome Web Store:** a Google account, the one-time **$5 developer registration fee**, two-step verification, the zip, the listing text, at least one **screenshot** (1280x800 or 640x400) and a 440x280 tile, a **privacy policy URL** (publish `PRIVACY.md`, e.g. on the Hallow GitHub Pages site), the permission justifications and data-use form (answers in `LISTING.md`). Review takes from days to weeks; `nativeMessaging` extensions get a closer look.
- **One code change after the first upload:** the store gives the extension a new ID. Hallow Keys must then also allow `chrome-extension://<store ID>/` (one line in `NativeHost`), so ship that in an update before telling anyone to install the store version.
- **Edge Add-ons / Opera add-ons:** free developer accounts (Microsoft Partner Center; addons.opera.com); the same zip and listing work.
- **Firefox Add-ons (listed):** a free addons.mozilla.org account, `hallow-keys-firefox-addons.zip`, the listing text, the privacy policy, and possibly the source if a reviewer asks (it's plain JavaScript, no build step). The add-on ID stays `hallow-keys@dom428.github.io`, so the app keeps answering it. Signing it **unlisted** (just for yourself) is described below.

## Firefox

The Firefox build is in the `extension-firefox` folder next to `HallowKeys.exe` (same code, a Firefox manifest with the add-on ID `hallow-keys@dom428.github.io` and background scripts instead of a service worker). Click **Connect browsers** in Hallow Keys first (it registers the app for Firefox under `HKCU\Software\Mozilla\NativeMessagingHosts\com.hallow.keys`, allowed only for that add-on ID).

- **To try it now:** Firefox > `about:debugging` > This Firefox > **Load Temporary Add-on** > pick `extension-firefox\manifest.json`. It stays until Firefox closes.
- **To keep it** (Firefox only keeps signed add-ons): sign it once for free with your own Mozilla account - nobody else can do this step for you.
  1. Make a free account at [addons.mozilla.org](https://addons.mozilla.org/developers/) and open the Developer Hub.
  2. **Submit a New Add-on** > **On your own** (unlisted - it isn't published in the store, Mozilla only signs it).
  3. Zip the *contents* of `extension-firefox` (manifest.json at the top of the zip) and upload it. The automatic review usually signs it within minutes.
  4. Download the signed `.xpi` and drag it into Firefox (or `about:addons` > gear > Install Add-on From File).
  5. In `about:addons` > Hallow Keys > **Permissions**, allow it on all websites (Firefox asks for site access separately).
  Do this again for new versions of the extension (the add-on ID stays the same, so the app keeps answering it). Unlike Chrome's fixed extension key, a Firefox add-on ID is only protected once it's signed under your account - so prefer the signed copy over a temporary one.
